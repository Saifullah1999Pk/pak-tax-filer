# 003 Document Upload + AI Extraction: Design

**Date:** 2026-11-03 · **Status:** Proposed · **Feature:** 003 (README milestone 3) ·
**Governed by:** [Constitution](../../../.specify/memory/constitution.md)

## Intent

README milestone 3: "Document upload + AI extraction (salary cert, bank profit cert) with
confidence scoring and a human confirm/correct step. Extraction accuracy eval dataset." A
logged-in user uploads a certificate, Claude reads the figures the tax engine needs, and the
user confirms or corrects every value before anything else can use it (Principle III). An eval
measures how accurate extraction really is (Principle VI).

## Scope

- **Upload:** PDF, JPG or PNG; at most 10 MB and 5 pages. The user chooses the type: salary
  certificate or bank profit certificate. Only the owner can see their documents (002's
  `current_user`).
- **Fields (figures only, no personal identifiers):**
  - Salary certificate: tax year, gross salary, taxable salary, tax deducted by employer.
  - Bank profit certificate: tax year, profit amount, tax withheld under §151.
- **Extraction:** each field gets a value, a confidence (high / medium / low) and where it was
  found (page number and the label as printed, e.g. "Gross Salary").
- **Review:** the document is shown beside its fields; low-confidence fields are highlighted;
  the user confirms or edits each field, then confirms the document. Only confirmed documents
  are usable by later features, enforced by the backend.
- **Eval:** a synthetic, labelled dataset and a script reporting per-field accuracy and how
  often wrong values were marked high confidence.

## Out of scope

Other document types; detecting the document type automatically; combining several
certificates; passing values to the tax engine (feature 004 reads confirmed documents);
background job queues.

## Decisions

- **Both PDFs and photos** (decided by Saifullah): Claude reads both natively; the eval
  measures photos separately so their accuracy is known, not assumed.
- **Approach A: one Claude call plus rule checks** (decided by Saifullah). One call per
  document using structured output (JSON matching the field list). Plain code then checks the
  result, and any failed check sets that field to low confidence:
  - amounts are valid non-negative numbers (stored as `Decimal`, Principle I);
  - tax deducted ≤ gross salary; taxable salary ≤ gross salary; tax withheld ≤ profit amount;
  - tax year looks like `2025-26` and matches the tax year in the user's taxpayer profile
    (feature 002; today only 2025-26). Uploading needs a profile (amended 2026-11-04).
- **Model chosen by the eval** (decided by Saifullah): start with Claude Opus 5.5; run the eval
  on Opus 5.5, Sonnet 5.5 and Haiku 5.5 and use the cheapest that meets the accuracy bar. The
  model is a setting, not hard-coded.
- **Extraction runs while the user waits**, with a progress indicator. *(Builder's call.)*
- **Statuses:** uploaded → extracting → needs review → confirmed, or failed. A failed
  extraction (API error, timeout, refusal) can be retried. A confirmed document can't be
  edited; the user deletes it and uploads again. *(Builder's call.)*
- **Original files are kept** in a local Docker volume so the review screen can show them;
  deleting a document deletes its file. *(Builder's call.)*
- **Eval set:** 20 synthetic certificates per type, generated by a script from known values
  across at least 4 layouts per type; each as a clean PDF and as a photo-like image (rotated,
  blurred, shadowed): 80 files in total. *(Builder's call.)*
- **Accuracy bar (proposed, lead may adjust):** at least 95% of fields exactly right on clean
  PDFs and 90% on photos; at most 2% of wrong values marked high confidence. *(Builder's
  call.)*
- **Eval in CI** runs when extraction code, the prompt or the eval data change, and on demand;
  not on every PR (about $2 a run on Opus 5.5, less with the Batch API). Needs an
  `ANTHROPIC_API_KEY` repository secret. *(Builder's call.)*
- **"Demo data only" notice** on the upload page (Principle V). *(Builder's call.)*

## Approaches

| Approach | Trade-off | Outcome |
|---|---|---|
| A. One call with self-rated confidence, plus rule checks | Simple and cheap; self-rated confidence isn't fully reliable, so rule checks, the eval and human confirmation back it up | **Chosen** |
| B. Extract twice and compare | Evidence-based confidence; double cost and time | Upgrade path if the eval shows A's confidence misleads |
| C. OCR first, then Claude on the text | New stack component; loses layout; Claude already reads images | Rejected |

## Known limitation

Synthetic certificates can't reproduce the full variety of real ones (unusual layouts, stamps,
handwriting, Urdu text, poor scans). A passing eval shows extraction works on our test set, not
that it will on real documents. Acceptable while the app is demo-only (Principle V); the eval
and accuracy bar must be re-checked against consented, anonymised real documents once legal
review allows them.

## Dependencies

- Features 001 (backend, database, CI) and 002 (`current_user`).
- An Anthropic API key with credits for development, testing and the CI eval. The Claude Pro
  subscription does not include API access; Saifullah is asking the lead.

## Done when

- A user can upload either document type as a PDF or photo, see extracted fields with
  confidence, correct them and confirm the document.
- Unconfirmed values can't be read by any other feature (tested at the API level).
- A user can't see or change another user's documents (tested).
- The eval runs on all 80 files and meets the accuracy bar with the chosen model.

## Left to the plan

document generator, the eval script, and the CI trigger rules.
